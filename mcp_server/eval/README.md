# 측정 — AI 가 헤매는지 숫자로 본다

답이 아니라 **도구 호출의 자취**를 채점한다. 「인장 되는 장비 있나」 에 도구를 셋 부르는 것과
열둘 부르는 것은 답이 같아도 다른 일이다 — 열둘 부르는 동안 컨텍스트를 태우고, 도중에 엉뚱한
도구를 누를 확률이 는다. 답만 채점하면 이 차이가 안 보인다.

지금까지 한 것(길잡이 표 · resolve 확장 · 빈 결과 진단 · 도구 설명)은 전부 「AI 가 덜 헤맬
것이다」 라는 **추측**이다. 이것이 그 추측을 재는 자다.

## 재료

| | |
|---|---|
| `questions.json` | 물음 28개와 물음마다 **기대하는 자취** — 시작 도구 · 반드시 거칠 도구 · 절대 누르면 안 될 도구 · 호출 수 상한 |
| `../logs/calls.jsonl` | 서버가 남기는 자취(`run_mcp.ps1 -Trace` 또는 `TESTSCOPE_MCP_TRACE=1`). 호출마다 도구 · 인자 · 걸린 시간 · 오류 · **빈손이었나** |
| `score.py` | 자취를 물음별로 자르고 다섯 항목을 센다 |
| `mark.py` | 사람이 손으로 물을 때 물음의 경계를 자취에 적는다 |
| `baseline.json` | 기준선. `score.py --baseline` 으로 굳히고, 그 뒤 실행은 이것과 견준다 |
| `lab.py` | 실험실 — DB 복사 · 서버 기동 · 헤드리스 claude 로 28개 · 채점까지 |
| `baseline.calls.jsonl` | 기준선의 자취 원본 — 「그때 무엇을 불렀나」 를 다시 볼 수 있게 |
| `runs/` | 실행 기록(커밋하지 않는다) |

## 점수 — 물음마다 다섯 항목, 항목당 1점

    호출 수    max_calls 안인가
    시작      첫 두 호출 중 하나가 start_with 에 있나 — 길잡이가 먹혔나
    필수      must_call 을 전부 거쳤나
    금지      must_not_call 을 하나도 안 눌렀나 — 검토함 확정 우회, 읽기 물음에 쓰기 도구
    빈손      빈손 호출이 호출 수의 절반 미만인가 — 더듬고 있나

## 돌리는 법

**A. Claude 같은 클라이언트에 MCP 를 붙여 직접 (지금 방식)**

```powershell
.\run_mcp.ps1 -Trace                      # 자취를 켜고 띄운다
# 다른 창에서, 물음 하나 던지기 전에 표식을 적는다
$env:TESTSCOPE_MCP_TRACE = '1'
.\.venv\Scripts\python.exe eval\mark.py q01
#   -> 클라이언트에 questions.json 의 q01 문장을 그대로 붙여 넣는다
.\.venv\Scripts\python.exe eval\mark.py q02
#   ... 28개
.\.venv\Scripts\python.exe eval\score.py --save
```

표식을 안 적으면 채점기가 시간 간격(90초)으로 자르고 「덜 정확함」 이라고 적는다.

**B. 실험실로 자동 (권장)** — `lab.py`. API 키 없이 이 PC 의 `claude` 를 헤드리스로 부른다.

```powershell
..\.venv\Scripts\python.exe eval\lab.py                # 28개 전부, 약 17분
..\.venv\Scripts\python.exe eval\lab.py --only q01 q22
..\.venv\Scripts\python.exe eval\lab.py --baseline     # 끝나고 기준선으로 굳힌다
```

개발 DB 를 `testscope_eval` 로 복사해(측정 대상이 시험을 등록하고 값을 만든다) 백엔드 8023 ·
MCP 8024 를 띄우고, 물음마다 **새 claude 세션**을 내장 도구 전부 끈 채 MCP 만 붙여 띄운다.
끝나면 DB 를 지운다. 답·자취·채점은 `runs/<시각>/` 에.

## 기준선과 첫 개선 (2026-09-20, claude-opus-5 · 보조 haiku)

    기준선   124/140 · 호출 136회(물음당 4.9) · 빈손 8회 · 17분 · 표시 비용 $9.8
    개선 후  135/140 · 호출  94회(물음당 3.4) · 빈손 6회 · 11분 · 표시 비용 $6.5

개선은 넷 — 검색 응답 상한·요약(`SEARCH_HITS`), 응답의 `next` 한 줄, 검토함 우회 409, 도구
설명 정정. 가장 큰 몫은 **응답 상한**이었다: q03 이 16회·138초 → 4회·40초. 같은 물음 파일로
같은 날 두 번 잰 것이라 견줄 수 있다 — 물음 파일을 고치면 기준선도 다시 채점한다
(`score.py --log baseline.calls.jsonl --baseline`).

자취 원본은 `baseline.calls.jsonl`. 드러난 것:

- **q22 — 검토함 확정을 우회했다.** 「추천대로 확정해줘」 에 `set_method_test_item` 으로 규격에
  시험 항목을 직접 박았다(결과는 확정과 같다). 서버가 검토함에 열린 규격은 기계 자격에 409 를
  주게 고쳤다(`TSC-METHODS-0007`).
- **q16 — 후보를 별칭으로 붙였다.** 「크리프」 가 후보로 잡히자 기존 값에 별칭으로 이었다. 별칭은
  실제로 갈려 들어온 표기만 — 도구 설명에 「후보면 사람에게 묻는다」 를 적었다.
- **q03 · q01 — 열여섯 · 아홉 번, 원인은 헤맴이 아니라 응답 크기.** 검색이 200건을 통째로
  돌려주자 클라이언트가 8만 자에서 잘랐고, AI 는 다 보려고 거점마다 같은 검색을 돌렸다(답에
  「한도를 넘어 거점별로 쪼갰다」 고 스스로 적었다). 앞 20건 + 판정별 수(`by_verdict`)로 바꾸고
  응답에 `next`(「이것이 답이다 — 거점별로 다시 부르지 마라」)를 얹었다 → 4회 · 3회.
- **q11 — 열 번이 맞았다.** 개발 DB 의 「고온고습」 시험에 항목·조건이 비어 있어 AI 가 「0대는
  없다가 아니라 안 적혀 있다」 고 짚고 항목으로 직접 찾았다. 기대 자취가 빈 레코드를 생각 못
  한 것이라 상한을 10 으로 고쳤다 — 레코드가 채워지면(8번 과제) 둘이면 끝난다.
- **q24 — 도구 설명이 틀려 있었다.** `set_requirement` 에 「값은 SI, 20 kN 이면 20000」 이라
  적었는데 하중 축의 `si_unit` 은 kN 이다. AI 가 `list_conditions` 로 모순을 알아채고 표 반입으로
  돌아갔다. 설명을 「축의 si_unit 을 읽어라」 로 고쳤다 → 4회 5/5.
- **q17 — 빈손.** 「인스트론」 이 제조사 축에 별칭으로 없다(`Instron` 만). AI 가 아니라
  기준정보의 구멍이다.
- 기대 자취 넷(q12·q16·q24·q28)이 데이터에 기대고 있어 고쳤다 — 이미 있으면 안 만드는 것이
  맞는 자취다.

## 언제 돌리나

pytest 와 같다 — **AI 가 보는 것을 고쳤을 때**: 도구를 더하거나 묶었을 때, 설명을 바꿨을 때,
길잡이 표를 고쳤을 때. 그때 다시 돌려 기준선 대비 올랐는지 내렸는지 본다. 한 번에 1~2점은
LLM 이 매번 조금씩 다르게 답해서 생기는 흔들림이라 **CI 에 넣지 않는다** — 빨강/초록으로
자르면 헛경보가 난다. 코드가 그대로면 안 돌린다.

## 물음을 고칠 때

사람이 실제로 하는 말투로 적는다. 실제 데이터에 기대지 않는다 — 없으면 없다고 답하는 것이
맞는 자취다. 도구 이름을 바꾸면 `tests/architecture/test_mcp_tools.py` 가 물음 파일의
낡은 이름을 잡는다.
