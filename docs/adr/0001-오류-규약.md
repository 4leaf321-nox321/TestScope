# 0001. 오류는 봉투에 담고 반드시 로그를 남긴다

## 결정

도메인 오류는 `AppError` 계열을 raise 하고, 응답 본문은 **오류 핸들러만** 만든다.
형식은 `{"error": {code, message, request_id, details}}` 이고 코드는
`TSC-<MODULE>-<NNNN>` 이다. 프레임워크가 내는 오류(405·라우팅 404)도 같은 봉투에
담는다.

## 배경

오류 응답을 라우트에서 직접 만들 수 있으면, 어떤 경로는 로그를 남기고 어떤 경로는
안 남긴다. 그 차이는 급할 때 생기고, 급할 때가 정확히 로그가 필요한 때다.

봉투를 안 씌운 오류가 하나라도 있으면 프론트의 파서가 그것을 읽다가 터진다.
그러면 화면에는 원인 대신 자바스크립트 예외가 뜨고, 사람은 **요청이 왜 실패했는지가
아니라 프론트가 깨졌다고** 읽는다.

## 대안

- **라우트가 직접 만든다** — 자유롭지만 위의 두 문제를 그대로 안는다.
- **로그만 강제한다** — 봉투가 갈리는 문제가 남는다.

## 결과

- `raise HTTPException` 은 이 저장소 코드에 한 줄도 없다. 핸들러에 오는 것은 전부
  프레임워크가 낸 것이다.
- `request_id` 가 응답·파일 로그·접근 로그·감사 기록 넷을 잇는 끈이 된다. 사용자가
  화면의 그 문자열을 그대로 전달하면 관리자가 요청의 전말을 볼 수 있다.
- 검증 실패도 **어느 칸이 왜 틀렸는지** 우리말로 말한다(`describe_validation`).
  영어 한 줄은 화면에서 아무도 안 읽는다.
